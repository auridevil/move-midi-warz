## What shipped (for the panel)

- **`evo.sync: 'bars' | 'cycle'`** (settings, saved, default `bars`; old settings without it load as bars; `every` stays
  the bar count). In `onTick` (`app.js`), cycle mode fires `evolveNow` when `evolveDue(t, cyc, m.origin)`: the tick where
  `(t − origin) % cycle === 0`, the same `m.cycleTicks(cycleOpts())` (conditions and dice repeat included) the bloom,
  the sun, the cycle caption and the slot "full cycle" switch use. Never on Play's own downbeat (t 0), never on a bar
  line as such. Bars mode is the old line, byte for byte.
- **`orbit2/src/poly/evolve-sync.js`** (pure): `nextEvolveTick(tick, cycle, mode, every, bar, origin)`, `evolveDue`,
  `cycleProgress`, `syncFrom`. `evolveDue(t)` IS `nextEvolveTick(t − 1) === t`, so the clock asks the very function the
  countdown reads. `scene.js beatsLeft` (the sun's numeral) is now derived from it (`ceil((nextEvolveTick − tick) /
  beat)`, same numbers as before), and the arc's crawl (`cycleProgress`) and the drift LEDs read it too.
- **The re-sync rule** (documented in the file): after a mutation that changes the cycle, the next call already reads
  the new cycle: the next alignment of the NEW pattern after the mutation tick, counted from the pattern's origin (the
  instant every lane and the sun count from), so the number on screen and the mutation can never disagree. It can be
  shorter than the new cycle (the origin's multiple falls sooner), never longer.
- **UI:** sheet → groove → evolve: `every` switch **bars · cycle** (`#evo-sync`); in cycle the gauge is replaced by the
  read-only line "every cycle · N beats" (`#evo-cycle`, N = the sun's stopped number, follows lane edits); the arc reads
  "EVOLVE · CYCLE" and crawls to the mutation; the caption "evolve in N beats" (the sun's number); the pill "evolve ·
  cycle". Tooltip: "Change the pattern each time every ring lines up again, the moment the sun reaches 0."
- **Drift page (`?drift`):** knob 1 is the every gauge, now `min: 0`: its lowest detent (0) reads "cycle" and means
  cycle mode; any step up is bars. Documented in the Move table (index.html, moveview.mjs, pages.js comment). No other
  mapping change; with `?drift` off nothing differs.
- Not touched: `lanes.js` (the model), `export.js`, the voices and DSP; `maxBars`, gravity, home-after and the weights
  run as before.

## Round 0 notes (the implementer, for round 1)

- **The re-sync is measured from the origin, not from the mutation tick.** The brief says "the next alignment of the NEW
  pattern, measured from the mutation tick". The sun and the bloom count from `m.origin`, and the lanes play from it, so
  that is where the new pattern really lines up; counting a full new cycle from the mutation tick would make the sun hit
  0 with no mutation (or the mutation land where nothing meets). The test asserts the gap to the next mutation is ≤ one
  new cycle. A reviewer who wants the other reading should say so as a MUST-FIX with a repro.
- **Bars mode's countdown is untouched** (`genProgress` / `barsToEvolve`, counting bar lines through meter changes);
  `nextEvolveTick(…, 'bars', …)` is the steady-meter form for display and tests, not read by the clock (the clock keeps
  counting bar lines, so a meter change cannot skew it).
- The sheet's every gauge now ranges 0–32 (0 = cycle), so dragging it to the bottom flips the mode and the gauge then
  hides (under the finger). The switch is the plainer route; the drag is the drift page's knob 1 in miniature.
- The dice stream for a cycle mutation is seeded by the beat number (`floor(t / PPQ)`), not the bar count: two
  mutations inside one bar (a cycle shorter than a bar) must not roll the same dice.
- `evo.sync` is not in the share link or the slots (settings only, like `every`).
